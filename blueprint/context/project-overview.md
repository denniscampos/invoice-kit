# Invoice Kit - Project Overview

> A fast, minimal invoice builder on Cloudflare. Make an invoice and download the
> PDF with no account; sign up when you want to save and manage them.

_Generated by `/overview` from `blueprint/project-plan.md` and
`blueprint/build-plan.md`. Don't hand-edit; change the plans and re-run._

## Problem

Making invoices by hand in Google Docs or similar tools is slow and repetitive.
Every invoice means re-typing the same sender details, rebuilding the same line
item table, and re-doing the same math. Nothing tracks what was sent or paid, so
history and status live in someone's memory or a folder of PDFs.

Invoice Kit makes invoice creation fast and repeatable: generate invoices from
templates, manage line items, keep the history in one place, and track whether
each one has been paid. The one-off case is served without an account, because
demanding a sign-up before someone has seen the product is the friction that
sends them back to Google Docs.

## Users

- **One-off users** - need a single invoice right now and will not sign up for
  it. They get the editor, the preview, and the PDF.
- **Freelancers** - send invoices regularly and want history and paid/unpaid
  status. Worth an account.
- **Contractors** - bill repeat clients with similar line items and want the
  previous invoice as a starting point.
- **Small business owners** - want a simple, current tool instead of bloated or
  dated invoicing software.
- **Self-hosters** - developers who clone the repo and run it against their own
  D1 and R2.

### Access tiers

| | Anonymous | Signed in |
| --- | --- | --- |
| Build an invoice, live preview | Yes | Yes |
| Choose a template | Yes | Yes |
| Download the PDF | Yes, rate limited | Yes |
| Save and retrieve invoices | No | Yes |
| Invoice list, status tracking | No | Yes |
| Logo and file uploads (R2) | No, client-side logo only | Yes |

The tier line is exactly the storage line: anonymous requests touch neither D1
nor R2.

## Features

MVP, in build-plan order. The headline is the **invoice editor with live
preview** (1 + 3): the form on the left and the rendered invoice on the right is
the thing users come for.

**The free path, items 1-5.** A complete, shippable product before the database
exists. Nothing is stored on the server.

1. **Invoice editor** - create an invoice with bill from, bill to, invoice
   details, payment terms, and notes.
2. **Line items** - add, edit, remove, reorder, and total multiple line items.
3. **Live invoice preview** - a minimal invoice template that updates as the form
   is filled out.
4. **Template selection** - switch between simple templates for both the preview
   and the final PDF.
5. **PDF generation** - render the HTML template to a downloadable PDF through
   Cloudflare Browser Rendering / Puppeteer, no account needed.

**The account path, items 6-13.**

6. **Accounts and auth** - sign up, sign in, sign out, and protected routes via
   Better Auth with D1.
7. **Invoice persistence** - save invoices to D1, scoped to the signed-in user.
8. **Draft handoff** - carry an in-progress anonymous invoice through sign-up and
   save it to the new account.
9. **Invoice list** - browse saved invoices with client, number, total, due date,
   and status.
10. **Invoice status tracking** - mark invoices draft, sent, or paid; overdue is
    derived from the due date.
11. **Invoice detail view** - open a saved invoice to view, edit, download, or
    change status.
12. **Delete and void** - delete a draft; void a sent invoice without erasing it.
13. **Logo upload** - upload a logo to R2 and attach it to a saved invoice.
14. **Previous invoice upload** - store invoice files created outside the app.

**Hardening and shipping, items 15-17.**

15. **Anonymous abuse protection** - rate limit the account-free PDF endpoint.
16. **Local and self-hosted setup** - documented clone-to-running path.
17. **Deployment readiness** - D1, R2, and Browser Rendering bindings verified.

Post-MVP: custom fields (18), tax and discount controls (19), invoice
duplication (20), client reuse (21), settings (22).

## Data model

Cloudflare D1 (SQLite). Files live in R2; D1 stores only the key and metadata.
Better Auth owns its own tables in the same database.

**Anonymous invoices are not in this model.** They live in `sessionStorage` as a
serialized draft until sign-up, when feature 8 writes them into `Invoice`. The
draft format should therefore mirror the `Invoice` + `LineItem` shape closely
enough that saving is a straight mapping, not a translation.

`sessionStorage` over `localStorage` is deliberate: the draft holds a third
party's name, address, and billed amount, and it should not outlive the tab on a
shared machine. It survives a refresh and the same-tab sign-up redirect, which is
all feature 8 requires.

**Locked decisions** that later features depend on:

- Money is stored as **integer minor units** (cents), never floats. Rounding on
  a float total is a bug you find at tax time.
- `currency` is a 3-letter ISO 4217 code stored per invoice, so historical
  invoices keep the currency they were issued in.
- Dates are ISO `YYYY-MM-DD` strings; timestamps are ISO 8601 UTC strings.
- Party details (bill from / bill to) are **copied onto the invoice**, not
  referenced. An invoice must keep the address it was sent with even after the
  client record changes. Feature 20 (client reuse) adds a source record to copy
  from; it does not turn these into foreign keys.
- **Overdue is derived, never stored.** Stored status is
  `draft | sent | paid | void`. A stored overdue flag would need a scheduled job
  to flip it and would be wrong for any invoice the job missed.
- **Voiding is a status, deleting is a delete.** A draft can be deleted outright.
  A sent invoice is voided and kept, because its number was already given to a
  client and a gap in the sequence is the kind of thing an accountant asks about.
- **`userId` on every user-owned row**, filtered in every query, never read from
  a request.

### User (Better Auth)

Better Auth generates and owns these tables; do not hand-write their schema.

- `user` - `id`, `email`, `emailVerified`, `name`, `createdAt`, `updatedAt`
- `session` - `id`, `userId`, `token`, `expiresAt`, plus IP and user agent
- `account` - credential rows, including the password hash
- `verification` - tokens for email verification and password reset

### Invoice

- `id` (text, uuid) - primary key
- `userId` (text) - to `user`, cascade delete; every query is scoped by it
- `invoiceNumber` (text) - user-visible, unique per user. Defaults to the next
  value in a per-user `INV-0001` sequence, and stays editable; uniqueness is
  enforced, the sequence is only a suggestion. Anonymous invoices have no
  sequence to draw from and default to `INV-0001`.
- `status` (text) - `draft` | `sent` | `paid` | `void`
- `templateId` (text) - which invoice template renders it (feature 4)
- `issueDate` (date), `dueDate` (date)
- `currency` (text) - ISO 4217
- `logoAssetId` (text, nullable) - to `Asset`
- `billFromName`, `billFromAddress`, `billFromCity`, `billFromRegion`,
  `billFromPostalCode`, `billFromCountry`, `billFromEmail`, `billFromPhone`,
  `billFromTaxId` (text)
- `billToName`, `billToAddress`, `billToCity`, `billToRegion`,
  `billToPostalCode`, `billToCountry`, `billToEmail`, `billToPhone`,
  `billToTaxId` (text)

`billFromTaxId` / `billToTaxId` are free-text and optional: VAT, ABN, EIN, GST,
and friends vary by country and there is no format worth validating centrally.
- `paymentTerms` (text, nullable)
- `notes` (text, nullable)
- `subtotal` (integer, minor units) - sum of line item totals
- `discountTotal` (integer, default 0) - stays 0 until feature 18
- `taxTotal` (integer, default 0) - stays 0 until feature 18
- `total` (integer) - `subtotal - discountTotal + taxTotal`
- `customFields` (text, JSON, nullable) - reserved for feature 17
- `createdAt`, `updatedAt` (text, ISO 8601)
- has many `LineItem`, has many `Asset`

**Derived status** (computed at read time, not a column):
`status === 'sent' && dueDate < today` renders as **overdue**.

### LineItem

- `id` (text, uuid) - primary key
- `invoiceId` (text) - to `Invoice`, cascade delete
- `position` (integer) - display order
- `name` (text)
- `description` (text, nullable)
- `quantity` (real)
- `rate` (integer, minor units) - price per unit
- `total` (integer, minor units) - `round(quantity * rate)`, stored so a saved
  invoice never re-computes to a different number

### Asset

One row per file in R2: logos (12) and uploaded historical invoices (13). Both
are account-only.

- `id` (text, uuid) - primary key
- `userId` (text) - to `user`, cascade delete
- `invoiceId` (text, nullable) - to `Invoice`; null for a logo not yet attached
- `kind` (text) - `logo` | `uploaded_invoice`
- `r2Key` (text) - object key, prefixed by user id so one user's objects are
  never adjacent to another's
- `filename` (text) - original name for download
- `contentType` (text), `sizeBytes` (integer)
- `createdAt` (text, ISO 8601)

Generated PDFs are not stored, so they get no `Asset` row. See Deployment.

## Tech stack

- **React Router 8 (SSR, framework mode)** - routes, loaders, and actions; the
  app shell and forms
- **React 19** - UI components
- **Cloudflare Workers** - runtime for the whole app (`workers/app.ts`)
- **Cloudflare D1** - SQLite storage for auth, invoices, line items, and asset
  metadata
- **Cloudflare R2** - object storage for logos and uploaded invoice files
- **Better Auth** - email and password auth, sessions, and password hashing,
  with its tables in D1
- **Cloudflare Rate Limiting** - protects the account-free PDF endpoint
- **Tailwind CSS v4** - styling, CSS-first config in `app/app.css`
- **shadcn/ui** - owned-in-repo UI primitives, added with its CLI
- **Cloudflare Browser Rendering / Puppeteer** - renders the HTML invoice
  template to PDF on demand
- **Vite 8 + TypeScript** - build and type safety
- **pnpm** - package manager

## Monetization

Not in v1. The goal is a useful, self-hostable invoice tool; monetization is a
later question if it comes up at all. Note that the anonymous/account split is
the shape a paid tier would eventually sit on, if that day comes.

## UI/UX

Minimal, clean, and fast. The editor is a two-pane layout: the form on the left,
a live invoice preview on the right that updates as the user types. The preview
uses the same template that renders the PDF, so what you see is what downloads.

The app opens straight into the editor. **No sign-up wall.** The account prompt
appears only when the user reaches for something that needs one, chiefly saving.
Sign-up and sign-in are plain, single-purpose pages.

Routes (derived from the features; names not fixed by the plans):

- `/` - the editor with live preview, usable anonymously
- `/sign-up`, `/sign-in` - plain auth pages
- `/invoices` - saved invoice list, signed in only
- `/invoices/:id` - detail view: view, edit, download PDF, change status
- `/invoices/:id/pdf` - PDF for a saved invoice
- PDF rendering for an anonymous invoice posts the draft to a render endpoint,
  since there is no id to fetch

## Deployment

Two supported paths, same code and same accounts on both.

**Local / self-hosted** (feature 15):

- `git clone`, `pnpm install`, copy `.dev.vars.example`, `pnpm dev`, with local
  D1 and R2 via Wrangler
- No third-party service keys to obtain; you make an account on your own instance
- The self-hoster owns their D1 database and R2 bucket

**Cloudflare** (feature 16):

- **Host**: Cloudflare Workers via Wrangler (`wrangler.json`, entry
  `workers/app.ts`). The plan says "Pages/Workers"; the scaffolded app is a
  Worker.
- **Build**: `pnpm build` - **Deploy**: `pnpm deploy` - **Dry run**: `pnpm check`
- **Bindings needed**: D1 database, R2 bucket, Browser Rendering. None are
  configured yet; `wrangler.json` currently holds only the sample
  `VALUE_FROM_CLOUDFLARE` var. Run `pnpm cf-typegen` after adding each.
- **Secrets**: Better Auth needs a signing secret (`BETTER_AUTH_SECRET`) and the
  deployed origin (`BETTER_AUTH_URL`). Set them with `wrangler secret put`, never
  in `wrangler.json`.
- **Migrations**: D1 migrations must run against the remote database before a
  deploy that depends on them.
- **Rate limiting on the anonymous PDF endpoint is a deploy blocker**, not a
  nice-to-have. It is the one unauthenticated route that reaches Browser
  Rendering, the slowest and most expensive call in the app.
- **PDFs are generated per request** and streamed to the browser, so there is no
  PDF storage cost and no stale-PDF problem. If render cost becomes a problem for
  signed-in users, caching a rendered PDF keyed on the invoice's `updatedAt` is
  the fix, not storing one at save time.

## Open questions

Resolve these in the plans, then re-run `/overview`.

1. **Nothing sends the invoice.** Status `sent` is a manual flag; the user still
   emails the PDF themselves. Worth confirming that is the intent for MVP.
   Not blocking: it changes nothing before feature 10.
2. **No upload limits.** Features 13 and 14 accept files with no stated size cap
   or accepted content types. Decide at feature 13, not before.
3. **Email verification and password reset** are unspecified. Better Auth
   supports both but they need an email sender, which the plans do not name and
   which would be the first third-party key in the self-hosting story. Decide at
   feature 6; deferring both is defensible for MVP.

Resolved and folded into the plans: anonymous draft storage (`sessionStorage`),
invoice numbering (per-user `INV-0001` sequence, editable), delete and void (now
MVP item 12), and tax/business IDs (real optional fields on both parties).
